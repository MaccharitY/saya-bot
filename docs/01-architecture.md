## 1. 核心设计思想

**一句话：把"QQ 怎么收消息"和"机器人怎么想"彻底切开。**

原因不是洁癖，是三个现实约束逼出来的：

1. 个人账号接非官方协议**有封号风险**，而且协议实现（NapCat 等）会随 QQ 版本变动而失效。
2. 需求 FR-10 要求以后能接官方机器人平台 —— 那套 API 和 OneBot 完全不同。
3. 课程报告要在**两周内**出数据，不能把时间耗在跟 QQ 客户端搏斗上。

所以内核只认**自己的领域模型**，不认 OneBot、不认官方 API。

## 2. 分层

```
真实 QQ 客户端 (NTQQ)
      ↕ 私有协议
[NapCat] ................ 第三方进程，我们不管它内部
      ↕ OneBot v11 (HTTP / WebSocket)
┌──────────────────────────────────────────────────┐
│  saya_bot                                        │
│                                                  │
│  adapter/  ── 接入层：把外部协议翻译成内部事件      │
│    base.py      统一接口 Adapter（收/发）          │
│    mock.py      本地假事件（**回放真 OneBot 格式**）│
│    onebot11.py  真后端（M5 才写）                  │
│         ↓ 内部领域事件（IncomingMessage）          │
│  core/  ──── 内核：业务逻辑，零外部协议依赖         │
│    trigger.py   该不该回？(FR-2)                  │
│    pipeline.py  编排：判定→组装→护栏→生成→过滤→发送 │
│    persona.py   人格与提示词组装 (FR-3)            │
│    guard.py     防注入护栏 (FR-4)                  │
│    memory.py    记忆读写 (FR-7)                    │
│         ↓                                        │
│  services/ ─ 能力层：每个能力一个模块，可替换        │
│    llm.py       文本对话（DeepSeek）               │
│    vision.py    看图 —— 内含两条路线 (FR-5/FR-9)    │
│    wiki.py      萌娘百科检索 (FR-6)                │
│    tools.py     MCP / 工具调用专用 CV 模型 (FR-9)   │
│         ↓                                        │
│  obs/  ───── 埋点层：记录每次调用的全量指标 (FR-8)   │
│    trace.py     写 JSONL，pre 的数据源             │
│    cost.py      token / 成本核算                   │
└──────────────────────────────────────────────────┘
                    ↓
              data/ (记忆库)  logs/ (trace)
```

**依赖方向是单向的**：`adapter → core → services → obs`。反方向依赖一律禁止（比如 `core` 里不许 `import` 任何 OneBot 的东西）。

## 3. 一条消息的生命周期

```
① adapter 收到外部事件
   → 归一化成 IncomingMessage(group_id, user_id, text, images[], ts, raw)

② core.trigger 判定
   → 不该回：直接结束（并记一条 skip 埋点，用于调参）
   → 该回：继续

③ core.pipeline 组装上下文
   → 最近 N 条群消息（滑动窗口）
   → 该用户的记忆 + 该群的话题记忆（FR-7）
   → 若疑似梗/角色问题：先查 wiki（FR-6）
   → 拉取图片：若是图片消息，走 vision 路线（FR-5）

④ core.guard 包装（关键）
   → 系统提示 / 人格 / 历史 与 群友原文 **分区隔离**
   → 群友内容一律标记为不可信数据
   → 检查是否命中越狱模式；命中则拒绝或降级

⑤ services 生成
   → llm.py 生成回复；若需看图则按 ADR-005 的路线分流
   → 每个调用点埋点：route / model / tokens / latency / cost

⑥ 输出过滤
   → 去掉不该出现的东西（系统提示片段、密钥、内部标记）
   → 长度/频率检查

⑦ adapter 发送 + obs 落盘
```

## 4. 数据落盘

| 数据 | 位置 | 说明 |
|---|---|---|
| 记忆库 | `project_main/data/`（gitignore） | 具体形式见 ADR-006【待确认】 |
| 埋点 trace | `logs/trace.jsonl`（gitignore） | 一行一个 JSON，pre 直接pandas读 |
| 实验原始数据 | `pre/experiments/`（**提交**） | 从 trace 提炼出的、可公开的对照数据 |
| 配置 | 环境变量 / `.env` | 密钥只在这里 |
| 原始截图 | `pre/requirement/`（**提交**） | 不可再生 |

⚠️ **trace 与 experiments 要分开**：trace 是运行日志（含真实 QQ 号、群号、隐私内容），**不提交**；experiments 是脱敏后的对照数据，**提交**。

## 5. 决策记录（ADR）

> 格式：`### ADR-NNN 标题` / 状态 / 背景 / 决定 / 理由 / 代价。
> 状态取值：`已定` / `待确认` / `已废弃（被 ADR-XXX 取代）`。

### ADR-001 内核与接入层解耦，adapter 统一接口
- **状态**：已定
- **背景**：FR-1 / FR-10；个人账号协议有封号风险且易失效。
- **决定**：定义唯一的 `Adapter` 接口（收事件回调 + 发消息方法）。内核只依赖内部领域模型 `IncomingMessage`，不依赖任何外部协议。
- **理由**：换后端不改内核；Mock 可跑测试（NFR-3）。
- **代价**：多一层翻译代码；领域模型要小心设计，漏了字段以后要改接口。

### ADR-002 主语言 Python 3.11
- **状态**：已定（项目所有者确认）
- **理由**：DeepSeek / 多模态 SDK、后续 CV 实验、数据处理、报告画图都在同一套工具链里。
- **代价**：并发不如 Node 顺手；但本项目量级（单账号少量群）无影响。

### ADR-003 Mock adapter 先行，且**回放真实 OneBot v11 事件格式**
- **状态**：已定
- **背景**：项目所有者对 QQ 机器人工具链不熟；本机无 docker；直接上真协议会把"未验证的内核"和"灰色地带的后端"两个变量同时引入。
- **决定**：M0-M4 全部在 `adapter/mock.py` 上开发。**关键**：mock **不编造假事件**，而是复刻 OneBot v11 的标准事件 JSON（群消息、私聊、图片消息、at 段等）。真后端定为 NapCat，M5 接入。
- **理由**：这样内核从第一天起就跑在"和 NapCat 将来喂进来的一模一样"的数据上，M5 只需把配置从 `mock` 换成 `onebot11`，内核零改动。
- **代价**：M0 之前要先抄对 OneBot 的事件格式；抄错要到 M5 才暴露（缓解：M5 前拿真实事件抓包核对一次）。

### ADR-004 LLM 接入方式
- **状态**：【待确认】
- **选项**：(a) 直连 DeepSeek 官方 OpenAI 兼容端点；(b) 走本机 CC Switch 代理（`127.0.0.1:15721`，Anthropic 格式）。
- **倾向**：**默认 (a) 直连**，但把 base_url / 协议做成可配置，两种都能切。
- **理由**：机器人是独立进程，依赖本机代理会多一个启动前置条件，且代理是给"壳"用的、随时会变。(b) 的好处是复用已有配额和映射表。
- **需要所有者决定**：用哪个 key、成本算谁的。

### ADR-005 视觉双路线开关（pre 的实验核心）
- **状态**：已定（设计层面）
- **决定**：`services/vision.py` 暴露统一接口 `describe(image, question) -> (answer, meta)`，内部按 `SAYA_VISION_ROUTE` 分流：
  - `direct_mllm`：直接把图片喂给多模态模型（如 `deepseek-v4.1-flash`）
  - `mcp_tools`：走工具调用，调专用 CV 模型（检测/分割/OCR/分类）后再交给文本模型归纳
  两条路线返回同样的 `meta`（route / model / tokens / latency / cost），写进同一条 trace。
- **理由**：报告要做公平对照，接口不统一就没法比。
- **代价**：`mcp_tools` 侧要额外搭 MCP server 或本地 CV 模型，工作量更大 —— **这是 M4 的主要风险，见路线图**。

### ADR-006 记忆的存储形式
- **状态**：【待确认】
- **选项**：(a) 本地 SQLite 结构化（人 → 属性表）；(b) JSON 文件 / 每群一个；(c) 向量库（语义检索）。
- **倾向**：**先用 SQLite**（结构化 + 够简单 + 支持删除与查询），语义检索以后再说。
- **理由**：FR-7 要求"可检索、可纠正、可遗忘"，结构化存储天然支持；向量库引入额外依赖与成本，P1 阶段没必要。
- **待确认**：是否现在就要"语义检索"级记忆。

### ADR-007 MCP 在报告里的定位
- **状态**：【待确认，等调研结果】
- **已知问题**：MCP（Model Context Protocol）是**协议/规范**，不是学术论文；而"多模态模型"是**模型**。两者不是同类事物，**直接比较会犯范畴错误**。
- **需要澄清**：报告里的对照应该是「**用多模态模型本体做视觉任务**」vs「**用工具调用外部专用 CV 模型做视觉任务**」，MCP 只是后者的协议实现之一。措辞定稿前必须问清楚老师/TA 的期待。
- **待办**：锚点论文调研（进行中）。

## 1. 核心设计思想

**一句话：把"QQ 怎么收消息"和"机器人怎么想"彻底切开。**

原因不是洁癖，是三个现实约束逼出来的：

1. 个人账号接非官方协议**有封号风险**，而且协议实现（NapCat 等）会随 QQ 版本变动而失效。
2. 需求 FR-10 要求以后能接官方机器人平台 —— 那套 API 和 OneBot 完全不同。
3. 课程报告要在**两周内**出数据，不能把时间耗在跟 QQ 客户端搏斗上。

所以内核只认**自己的领域模型**，不认 OneBot、不认官方 API。

## 2. 分层

```
真实 QQ 客户端 (NTQQ)
      ↕ 私有协议
[NapCat] ................ 第三方进程，我们不管它内部
      ↕ OneBot v11 (HTTP / WebSocket)
┌──────────────────────────────────────────────────┐
│  saya_bot                                        │
│                                                  │
│  adapter/  ── 接入层：把外部协议翻译成内部事件      │
│    base.py      统一接口 Adapter（收/发）          │
│    mock.py      本地假事件（**回放真 OneBot 格式**）│
│    onebot11.py  真后端（M5 才写）                  │
│         ↓ 内部领域事件（IncomingMessage）          │
│  core/  ──── 内核：业务逻辑，零外部协议依赖         │
│    trigger.py   该不该回？(FR-2)                  │
│    pipeline.py  编排：判定→组装→护栏→生成→过滤→发送 │
│    persona.py   人格与提示词组装 (FR-3)            │
│    guard.py     防注入护栏 (FR-4)                  │
│    memory.py    记忆读写 (FR-7)                    │
│         ↓                                        │
│  services/ ─ 能力层：每个能力一个模块，可替换        │
│    llm.py       文本对话（DeepSeek）               │
│    vision.py    看图 —— 内含两条路线 (FR-5/FR-9)    │
│    wiki.py      萌娘百科检索 (FR-6)                │
│    tools.py     MCP / 工具调用专用 CV 模型 (FR-9)   │
│         ↓                                        │
│  obs/  ───── 埋点层：记录每次调用的全量指标 (FR-8)   │
│    trace.py     写 JSONL，pre 的数据源             │
│    cost.py      token / 成本核算                   │
└──────────────────────────────────────────────────┘
                    ↓
              data/ (记忆库)  logs/ (trace)
```

**依赖方向是单向的**：`adapter → core → services → obs`。反方向依赖一律禁止（比如 `core` 里不许 `import` 任何 OneBot 的东西）。

## 3. 一条消息的生命周期

```
① adapter 收到外部事件
   → 归一化成 IncomingMessage(group_id, user_id, text, images[], ts, raw)

② core.trigger 判定
   → 不该回：直接结束（并记一条 skip 埋点，用于调参）
   → 该回：继续

③ core.pipeline 组装上下文
   → 最近 N 条群消息（滑动窗口）
   → 该用户的记忆 + 该群的话题记忆（FR-7）
   → 若疑似梗/角色问题：先查 wiki（FR-6）
   → 拉取图片：若是图片消息，走 vision 路线（FR-5）

④ core.guard 包装（关键）
   → 系统提示 / 人格 / 历史 与 群友原文 **分区隔离**
   → 群友内容一律标记为不可信数据
   → 检查是否命中越狱模式；命中则拒绝或降级

⑤ services 生成
   → llm.py 生成回复；若需看图则按 ADR-005 的路线分流
   → 每个调用点埋点：route / model / tokens / latency / cost

⑥ 输出过滤
   → 去掉不该出现的东西（系统提示片段、密钥、内部标记）
   → 长度/频率检查

⑦ adapter 发送 + obs 落盘
```

## 4. 数据落盘

| 数据 | 位置 | 说明 |
|---|---|---|
| 记忆库 | `project_main/data/`（gitignore） | 具体形式见 ADR-006【待确认】 |
| 埋点 trace | `logs/trace.jsonl`（gitignore） | 一行一个 JSON，pre 侧可直接用 pandas 读 |
| 实验原始数据 | `pre/experiments/`（**提交**） | 从 trace 提炼出的、可公开的对照数据 |
| 配置 | 环境变量 / `.env` | 密钥只在这里 |
| 原始截图 | `pre/requirement/`（**提交**） | 不可再生 |

⚠️ **trace 与 experiments 要分开**：trace 是运行日志（含真实 QQ 号、群号、隐私内容），**不提交**；experiments 是脱敏后的对照数据，**提交**。

### ADR-001 内核与接入层解耦，adapter 统一接口
- **状态**：已定
- **背景**：FR-1 / FR-10；个人账号协议有封号风险且易失效。
- **决定**：定义唯一的 `Adapter` 接口（收事件回调 + 发消息方法）。内核只依赖内部领域模型 `IncomingMessage`，不依赖任何外部协议。
- **理由**：换后端不改内核；Mock 可跑测试（NFR-3）。
- **代价**：多一层翻译代码；领域模型要小心设计，漏了字段以后要改接口。

### ADR-002 主语言 Python 3.11

- **代价**：并发不如 Node 顺手；但本项目量级（单账号少量群）无影响。

### ADR-004 LLM 接入方式 —— **定案**
- **状态**：**已定（2026-10-15）**：走 **DeepSeek 官方 API**
- **决定**：
  - 端点（OpenAI 兼容）：`https://api.deepseek.com`。官方**同时**提供 Anthropic 兼容端点 `https://api.deepseek.com/anthropic`，但我们用 **OpenAI 兼容** —— `tools` 参数用起来更直接。
  - 模型名：**`deepseek-flash`**。
    ⚠️ **不是**实验室文档里的 `deepseek-v4.1-flash` —— 那是**版本名**；官方**模型名**就叫 `deepseek-flash`。旧名 `deepseek-v4-flash` / `deepseek-v4-flash-vision-exp` 仍可调用，但后台已由 DeepSeek-V4.1-Flash 承接。
  - 该模型**原生支持图像理解**，且**完整支持 function calling**（OpenAI 标准 `tools` / `tool_choice`，另有 `strict` 模式保证输出符合 JSON Schema，Beta）。
- **理由**：机器人是独立进程，直连官方没有中间依赖。本机 CC Switch 代理是给"壳"用的，配置随时会变。
- **代价 / 注意**：
  - ⚠️ **`deepseek-v4-pro` 不支持图像理解**（只支持文本）—— 别把任何槽切过去。
  - 图片格式 JPEG/PNG/GIF/WebP，**按文件实际内容判断**，不看扩展名或 MIME 声明。
  - base64 内联的图片数据计入 **48 MiB 请求体上限**。
  - 密钥只放 `project_main/.env`，永不进仓库。
- **来源**：DeepSeek 官方文档一手核实（2026-10-15，用 `tools/fetch.py` 抓取）
- **附注（更强的证据）**：其实**本项目的开发会话自身就是证据** —— 它正跑在同一个模型（v41f）上，
  靠 function calling 驱动文件读写与命令执行。**模型会调工具，看它在不在真实使用里就知道了**，
  查文档只是确认"公开 API 暴露了对应的参数"。两者的区别见 `pre/11` 第 8.1 节。

### ADR-005 视觉三路线开关（实验的核心机制）
- **状态**：已定。**操作定义见 [../pre/12-experiment-design.md](../pre/12-experiment-design.md)**
- **共同前提**：三条路线**共用同一个大脑 `deepseek-v4.1-flash`**，唯一变化的是"图片由谁处理"。
- **决定**：`services/vision.py` 暴露统一接口 `describe(image, question, route) -> (answer, meta)`，按 `SAYA_VISION_ROUTE` 分流：
  - `direct`（路线 A）：图片**直接进主模型 prompt**，视觉全由 v41f 本体做
  - `delegated`（路线 B）：图片**完全不进主模型**；附属处理图片，只把**文本结果**交给 v41f
  - `hybrid`（路线 C）：附属出结构化产物（框/掩码/编号），`[原图 + 产物]` 一起进 v41f
  三条路线返回同样的 `meta`（route / model / tokens / latency / cost），写进同一条 trace。
- **理由**：报告要做公平对照，接口不统一就没法比；**共用大脑才能把"架构差异"和"模型差异"分开**。
- **待定**：路线 B / C 里的"附属"是**通用视觉大模型**还是**专用 CV 模型**（见 pre/12 第 3 节）——**未定，阻塞实现**。
- **代价**：路线 B 要搭 MCP server；路线 C 还要做画框标注。工作量明显大于路线 A。

### ADR-006 记忆的存储形式
- **状态**：【待确认】
- **选项**：(a) 本地 SQLite 结构化（人 → 属性表）；(b) JSON 文件 / 每群一个；(c) 向量库（语义检索）。
- **倾向**：**先用 SQLite**（结构化 + 够简单 + 支持删除与查询），语义检索以后再说。
- **理由**：FR-7 要求"可检索、可纠正、可遗忘"，结构化存储天然支持；向量库引入额外依赖与成本，P1 阶段没必要。
- **待确认**：是否现在就要"语义检索"级记忆。

### ADR-007 MCP 在报告里的定位
- **状态**：**已定（2026-10-15）—— 走三条路线**（A 纯 MLLM / B 外包专用 CV + 编排 / C 混合）。报告语言 **中文**（四节标题保留英文）。
- **调研证实了这个担忧**：领域代表作 **Set-of-Mark**（arXiv 2310.11441）本身就是**混合路线**——用分割模型出候选、再让 MLLM 做语义推理。也就是说现实中**最强的做法往往既不是纯 A 也不是纯 B**。
- **采用的报告主线**：不比"谁更好"，而比"**什么任务该走哪条路**"：
  - 路线 A：视觉任务**全部交给主模型本体**（v41f 直接看图）
  - 路线 B：视觉任务**全部外包给"附属"**（附属是通用视觉大模型还是专用 CV 模型，见 ADR-005 / `pre/12` 第 3 节，**尚未定**）
  - 路线 C：**混合**——附属出候选，主模型做语义推理（SoM 一类）
- **理由**：这样选题不再犯范畴错误；已知锚点论文（SoM / VisionLLM / LMM-Det / COUNTS）全部能自然纳入；而且**自己的实测数据正好回答"该走哪条"**——这恰是报告最有价值的部分。
- **代价 / 风险**：三条路线的实验量比两条大，需按 M3 的分层测试集控制规模。
- **待办**：定稿前跟老师或 TA 确认一句措辞。

### ADR-008 真 QQ 优先；Mock 降级为测试夹具
- **状态**：已定（2026-10-15，取代 ADR-003 的排期部分）
- **背景**：项目所有者备好了 QQ 账号（自述 SVIP9），要求**直接接真 QQ**，不再等内核在 Mock 上跑通。本机已装 QQ NT（`D:\Program Files\Tencent\QQ\QQ.exe`），NapCat 的前提条件满足。
- **决定**：
  1. **OneBot v11（NapCat）成为主开发路径**，从 M5 前移到 **M1**。
  2. `adapter/base.py` 的统一接口**不变**（ADR-001 仍然有效）——这是本次改动不伤筋动骨的原因。
  3. `adapter/mock.py` **保留但降级**：改为**自动化测试夹具**，继续回放真实 OneBot v11 事件格式（NFR-3 可测试性仍需要它）。
- **理由**：真事件驱动开发能尽早暴露真实数据里的边角情况（富媒体、at 段、撤回、被禁言、图片 CDN 过期等），这些是拍脑袋编不出来的。
- **代价 / 风险**：
  - **封号风险从"以后"变成"现在"**。所有者认为 SVIP 等级高、风控更宽容——⚠️ **此说法无公开证据支持**，按"无特殊保护"对待。一旦被封，损失的是这个 QQ 账号本身。
  - NapCat 需要给 QQ 客户端打补丁或替换启动器，**可能弄坏本机 QQ** → 安装前**先备份 QQ 安装目录**，确认可回滚。
  - 开发节奏被 QQ 客户端版本更新绑架（协议失效即中断）。缓解：内核与 adapter 解耦，Mock 夹具保证 QQ 侧挂了也能继续开发与测试。
  - 缓解封号影响：**把真号出的数据只在本地用，不要在报告/截图里暴露 QQ 号与群号**。

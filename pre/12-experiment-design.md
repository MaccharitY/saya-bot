## 1. 共同前提：同一个大脑

**三条路线共用同一个大脑：`deepseek-v4.1-flash`（v41f）**，它负责大部分事（对话、编排、推理）。

**唯一变化的东西：视觉任务由谁做。**

这个约束是硬性的。如果三条路线用了不同模型，测出来的就是"模型差异 + 架构差异"的混合物，**老师/TA 一句"会不会只是模型本来就强"就能问倒**。

## 2. 三条路线

### 路线 A · 纯自看（`direct`）

```
图片 → v41f（多模态）→ 答案
```
图片**直接进主模型 prompt**，视觉任务全部由 v41f 本体承担。

### 路线 B · 纯外包（`delegated`）

```
图片 → 附属（经 MCP）→ 文本结果 → v41f → 答案
```
图片**完全不进主模型**。附属处理图片，只把**文本**交给 v41f。
→ 注意这个干净的可测性质：**路线 B 里主模型根本不需要视觉能力**。

### 路线 C · 协同（`hybrid`）

```
图片 → 附属 → 结构化产物（检测框 / 掩码 / 编号标注）
                    ↓
        [原图 + 产物] → v41f（多模态）→ 答案
```
附属做**可量化的部分产物**（定位、分割、计数、编号），v41f 基于"图 + 结构化产物"做**语义推理**。这正是 Set-of-Mark 的做法。

## 3. "附属" = 专用 CV 模型（**已定**，2026-10-15）

路线 B / C 里的"附属"**确定为专用 CV 模型**（YOLO / GroundingDINO / PaddleOCR / SAM），**不是**另一个通用视觉大模型。

- **路线 B 的本质是"工具化"**：把可量化的子任务（检测 / 分割 / OCR）交给确定性模型，只把结构化文本交给 v41f。
- **为什么不用"通用视觉大模型级联"**（原来记为 B1）：那种做法的价值在于"**主模型没有视觉能力时补一只眼睛**"，而 v41f **本来就能看图**，再套一层视觉模型很可能只是白交一层开销。**不作为主实验组。**
- **文献依据**：MLLM 在计数、小目标、OCR、细粒度、空间关系六类任务上有系统性短板（CountQA、MMVP、CC-OCR、COUNTS、LMM-Det…）；路线 C 的代表作 Set-of-Mark 用的也正是分割模型出候选。见 [`11-literature.md`](11-literature.md)。

> **备选（本实验不采用）**：把附属换成一个通用视觉大模型，就变成"模型级联"。
> 若日后想补测这一组，单开一个 `experiment_tag` 跑即可，接口不用改。

| 组 | 路线 | 附属 | 图片进主模型？ |

## 5. 测试集

### ✅ 已建好（2026-10-16）：`pre/experiments/testset/`

**105 条 / 73 张图，四个难度层。标准答案是算出来的，不是标的。**

来源 **coco128**（YOLO 格式标注，含每张图里每个框的类别与坐标），
由 [`../../project_main/experiment/build_testset.py`](../../project_main/experiment/build_testset.py) 自动生成。

| 层 | 条数 | 判据 | 出题 | 预期 |
|---|---|---|---|---|
| `counting` | 30 | 同一类 ≥3 个 | 「图里有多少个X？只回答一个阿拉伯数字」 | **差异最大**（文献反复证伪 MLLM 计数） |
| `small` | 30 | 最大框占图面积 <10% | 「图里最主要的东西是什么」 | B/C 明显优 |
| `fine` | 30 | 含子集里的稀有类 | 同上 | A 略优（语义知识） |
| `common` | 15 | 只含常见类 | 同上 | 三路线接近（对照组） |

> **105 条 / 73 张图**，各层 30/30/30/15（新集合是旧集合的超集）。

> coco128 里只有 15 张图符合该层判据，不是参数限制。
> 完整记录见 [`13-experimental-protocol.md`](13-experimental-protocol.md) §4。

**判分**：`expect_keywords` 全部命中才算对。⚠️ 这是**简化判据** ——
偏爱包含关键词的回答，不判语义，而且**子串匹配有真实的跨题冲突**
（`3 ⊂ 13`：7 条期望 `3`、4 条期望 `13`；`马 ⊂ 斑马`：fine 层 1 条期望 `马`）。
2026-10-16 已加"数字按边界匹配 + 中文子串识别"，但这条局限仍必须写进 methodology。

**可复现**：挑图按文件名排序，同样的数据永远挑出同样的图。
图片本身 gitignore（COCO 图来自 Flickr，各有其许可，不适合直接分发）；
`manifest.json` 提交，照脚本能重建。

### ⚠️ 缺一层：含文字（OCR）

**COCO 不含文字标注**，所以设计里的第 5 层**没有做**。这一层得另找来源：

- 选项 A：Wikimedia Commons 的标志牌/招牌类图（CC 许可，要人挑）
- 选项 B：**自己合成**（用 PIL 把已知文本渲染到图上）—— 标准答案百分百准确，
  但离真实场景远
- 选项 C：从群里收集真实截图（最贴近使用场景，但有隐私问题且要人工标注）

**没有这一层不影响主结论**（计数与小目标两层已经足够支撑三条路线的对比），
但报告里要**明确写出这个缺口**，不能装作五个层都覆盖了。

### 控制条件

- 固定 prompt 与温度；**三条路线共用同一个大脑**（见第 1 节）
- **配对设计**：同图同问，三条路线各跑一次
- 延迟报 P50/P95，**并同时报输出 token 数**（长回答自然慢，不报就没法比）
- 跑之前先记**环境基线**（见第 6 节）

## 6. 指标

| 指标 | 怎么量 |
|---|---|
| 准确率 | **关键词二元判据**（`expect_keywords` 全部命中 = 对），按难度层分别报。⚠️ 本节原来写的"检测 mAP@0.5 / 计数 MAE"**没有实现** —— 实际判据以 [`13-experimental-protocol.md`](13-experimental-protocol.md) §5 为准；误报会算成正确（门槛偏松，报告里要写） |
| 延迟 | 端到端 **P50 与 P95**（不是只有平均值） |
| 成本 | 见下 |
| 失败率 | 超时 / 报错 / 拒答。**工具链失效也算失败**（见 `11-literature.md` 第 8.1 节的一手观察：瓶颈常不在模型而在工具链） |
| 幻觉率 | 在图中不存在的东西上编造（POPE 式探测）。⚠️ **没有实现**，见 §8 |
| 可解释性 | 能否给出 bbox / 置信度 / 依据。⚠️ 路线 C 有编号框，A/B 没有对应量 |

### ⚠️ 测延迟前必须先固定环境（**真实教训**）

2026-10-15 真机联调时踩到：机器人的回复延迟在 **1.1 秒 ~ 19 秒**之间乱跳，
中位数 6.2 秒，9 条里 6 条超过 5 秒 —— 而模型本身只要几百毫秒。
查到最后是**香港代理劫持了 WSL 的 DNS**，解析一个域名要等 10 秒超时。
关掉代理后：**DNS 从 11.05s 降到 0.01s，往返从 11.32s 降到 0.11s**。

**如果不查出这个，报告里的「延迟」测的会是"WSL 的 DNS 抽风速度"，而不是两条视觉路线的快慢。**

**因此实验必须做到**：

1. **跑数据前先记录环境基线**：DNS 解析耗时、到模型端点的往返、是否走代理
2. **跑数据期间环境保持同一状态**（代理开/关状态不能中途变）
3. 延迟报 **P50 与 P95**，并**同时给出环境基线**，让读者能判断哪些是架构差异、哪些是环境噪声
4. 长输出（几百 token）会自然变慢 —— 报延迟时要**同时报输出 token 数**，否则不可比

详见 [`../docs/04-napcat-deployment.md`](../docs/04-napcat-deployment.md) 坑三。

## 7. ⚠️ 成本口径（答辩最容易被问的点）

- 路线 **A / B1 / C 的模型部分**：按 API token 计费 → 有明确账单
- 路线 **B2 / C 的 CV 部分**：本地算力 → **没有 API 账单**，只有硬件折旧 + 电费

**两者不能直接相加。** 报告里必须分列两种口径：

- **边际 API 成本**（每千次调用多少钱）
- **本地算力摊销**（按 GPU 时价折算）

并说明：本地模型是**前期投入换长期低边际成本**，图片量大时优势才显现。**忽略这一点的对比是无效的。**
